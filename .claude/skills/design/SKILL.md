# design

使用本技能把已经澄清的想法转化为可沉淀、可评审、可指导后续版本规划的设计文档。

## 定位

`design` 位于 `clarify` 之后、版本规划之前。

它负责回答：

- 这个需求应该如何被设计？
- 需要哪些设计子域参与？
- 设计结论应该沉淀到 `docs/` 的哪里？
- 后续版本规划可以依据哪些稳定设计产物继续推进？

`design` 不负责：

- 重新澄清用户原始想法。
- 拆版本计划。
- 执行具体开发任务。
- 做代码评审、测试或安全审查。
- 替用户发散出未确认的大方向。

如果输入仍然含糊，先回到 `clarify`，不要强行设计。

## 输入

进入 design 前，优先读取已有上下文：

- 用户当前说明。
- clarify 阶段已经整理出的内容。
- `.workflow/decisions.md` 中相关原始意图、关键决策和决策变更。
- `.workflow/progress.md` 中当前状态，只作为背景参考。
- 现有 `docs/` 中相关长期文档。

## 路由原则

`design` 是一个路由型技能。

先判断当前设计任务涉及哪些设计子域，再读取对应 reference。设计子域不是互斥关系；一个复杂设计可以同时加载多个 reference。

初始子域包括：

| 场景 | reference |
| --- | --- |
| 用户目标、功能边界、产品流程、信息架构、体验路径 | `references/product.md` |
| UI/UX 原则、页面结构、交互模式、视觉规范、可用性 | `references/ui-ux.md` |
| 原型设计、低保真/高保真草图、页面状态、用户操作路径 | `references/prototype.md` |
| 前端模块划分、组件边界、状态管理、路由、前端工程约束 | `references/frontend.md` |
| 系统分层、模块关系、技术选型、边界、演进策略 | `references/architecture.md` |
| 接口定义、请求响应、协议、鉴权、兼容性 | `references/api.md` |
| 数据模型、表结构、字段、关系、索引、迁移 | `references/database.md` |
| 业务概念、业务规则、状态流转、计算规则、约束 | `references/business-rules.md` |
| 异常场景、错误码、失败处理、重试、降级、边界情况 | `references/error-handling.md` |

如果任务涉及未覆盖的设计子域，先用当前最接近的 reference 工作，并在输出中记录“需要补充的设计子域”。不要临时创造一套庞大新体系。

## 设计深度

根据任务复杂度决定设计深度。

轻量设计适用于：

- 单点功能。
- 影响范围清晰。
- 不涉及多模块、多角色、多状态或数据迁移。

复杂设计适用于：

- 跨模块或跨系统。
- 涉及 UI/UX、前端结构、API、数据库、状态机、权限、安全、性能或迁移。
- 存在多个可行方案，需要权衡。

复杂设计中，可以使用“多方案对比”：给出 2-3 个候选方案，说明取舍，再收敛到推荐方案。不要为了显得完整而制造无意义方案。

## 新项目与旧项目

设计阶段必须区分当前是新项目还是已有项目，这会影响设计方式、信息来源和改动策略。

### 新项目

新项目没有已有约束，设计空间更大，但也更容易选错方向。

设计时应：

- 查询当前官方文档或可信来源，确认推荐方案没有过时。不要凭记忆假设技术选型、框架版本或最佳实践。
- 在输出中说明推荐方案、推荐原因、不选其他常见方案的原因。
- 关注升级风险、生态成熟度和维护成本。

### 旧项目

旧项目已有约定、代码和历史决策，设计的首要约束是**沿用和补齐**。

设计时应：

- 先识别项目当前的技术栈、目录结构、编码约定和已有文档。
- 判断现有约定是否足以支撑需求。
- 识别过时、缺失或混用的问题。
- 优先小步补齐，不要轻易推翻重写。
- 只有现有方案无法满足需求时，才提出迁移方案，并明确迁移成本和风险。

无论新旧项目，设计文档中都应显式记录技术栈或项目约束。

## 输出位置

设计产出写入 `docs/` 下合适位置，而不是统一堆到 `docs/specs/`。

选择位置时遵循：

- 长期可复用的设计放入 `docs/`。
- 按内容性质选择或创建子目录。
- 保持目录层级清晰，不要把所有设计文档平铺在一个目录。
- 修改 `docs/` 时，同步更新对应目录的 `index.md`。

常见位置示例：

```text
docs/specs/product/
docs/specs/ui-ux/
docs/specs/prototype/
docs/specs/frontend/
docs/specs/architecture/
docs/specs/api/
docs/specs/database/
docs/specs/business-rules/
docs/specs/error-handling/
docs/adr/
docs/research/
```

这些只是示例，不是固定要求。具体目录应根据项目已有结构和文档性质决定。

## 模板使用

如果 `docs/templates/` 中存在与当前设计子域匹配的模板，优先使用该模板。

如果模板缺失，可以直接按 reference 中的输出结构生成设计文档。不要为了补模板而中断设计流程。

## 输出质量要求

设计文档应该做到：

- 保留用户原始意图，不擅自替用户改变方向。
- 明确上下文、目标、非目标、决策、风险和开放问题。
- 能指导后续版本规划和任务拆解。
- 对关键规则给出可验证的描述。
- 对未知项明确标记，不伪装成已决策。
- 避免空泛、宏大、不可执行的表述。

## 基本输出结构

不同 reference 可以定义更具体的模板，但每份设计文档至少应包含：

```markdown
# 标题

## 背景

## 目标

## 非目标

## 设计内容

## 关键决策

## 风险与权衡

## 开放问题

## 后续衔接
```

“后续衔接”用于说明该设计如何进入版本规划、任务拆解或其他设计子域。

## 执行流程

1. 判断输入是否足够进入 design；不足则建议回到 clarify。
2. 读取相关上下文和现有 docs。
3. 判断需要哪些设计子域。
4. 读取对应 references。
5. 如有合适的 `docs/templates/` 模板，则按模板生成；否则按 reference 输出结构生成。
6. 生成或更新 `docs/` 下合适位置的设计文档。
7. 同步更新该目录的 `index.md`。
8. 简短汇报产出位置、采用的设计子域和仍未解决的问题。
